# Phase 3 Home / Miniatures smoke harness

These scripts exercise the **production renderer**, not stories or development Electron.
They never build implicitly. Run only after the coordinator approves the current
production output; do not build into a shared worktree while another build is running.
All commands use the repository's exact `.nvmrc` Node **22.22.2**.

## Safe plan mode

```sh
export PATH="$HOME/.nvm/versions/node/v22.22.2/bin:$PATH"
EVIDENCE="$HOME/Desktop/REPOS/PERSONAL/paint-tracker-audit/graphql-phase-3-evidence"
node scripts/smoke-home-miniatures-browser.mjs "$EVIDENCE/browser/plan"
node scripts/smoke-home-miniatures-native.mjs "$EVIDENCE/native/plan"
node scripts/smoke-home-miniatures-docker.mjs "$EVIDENCE/docker/plan"
```

Without `--run`, each writes an honest **NOT RUN** result. Nothing is launched,
seeded, built, pulled, or installed. Do not interpret planning, successful builds,
unit tests, or browser success as a packaged-native pass.

## Build handoff (coordinator only)

The normal app build is `NX_SKIP_NX_CACHE=true npm run build`. First run Chromium
against that output; fix runtime errors and repeat before packaging. Once stabilized:

```sh
node scripts/package-desktop-server.mjs electron
RELEASE=$(mktemp -d /tmp/paintwarden-graphql-phase3-release-XXXXXX)
(cd apps/paintwarden-electron && CSC_IDENTITY_AUTO_DISCOVERY=false \
  ../../node_modules/.bin/electron-builder --mac --dir --arm64 --publish never \
  -c.mac.identity=null -c.mac.notarize=false -c.directories.output="$RELEASE")
# Expected app: "$RELEASE/mac-arm64/Paintwarden.app"
```

This produces a real `.app` with the production preload/main process and freshly
packaged server/native SQLite binary. It is **not** a signed/notarized distribution
or installation test. Repackage after any main/preload/server/UI change. The harness
hashes the executable, ASAR, server, schema, Node binary, and every packaged web asset.

Build a uniquely tagged Docker image only after approval:

```sh
docker build --tag paintwarden:graphql-phase3-smoke .
```

The Docker runner accepts an **existing inspected image ID**; it never builds or
pulls and uses `--pull=never`. An existing image's provenance must match the tested
revision; a successful browser run does not establish that.

## Actual execution

Use new evidence subdirectories for each attempt, including failed attempts:

```sh
node scripts/smoke-home-miniatures-browser.mjs "$EVIDENCE/browser/run1" --profile large --run
node scripts/smoke-home-miniatures-browser.mjs "$EVIDENCE/browser/run1" --profile stress --run
node scripts/smoke-home-miniatures-native.mjs "$EVIDENCE/native/run1" \
  --app "$RELEASE/mac-arm64/Paintwarden.app" --run
node scripts/smoke-home-miniatures-docker.mjs "$EVIDENCE/docker/run1" \
  --image 'sha256:EXPLICIT_APPROVED_IMAGE_ID' --run
```

Browser optionally accepts `--web-dist ABSOLUTE_PATH`. Its server is the existing
`apps/paintwarden/dist/server.mjs`; both must correspond to the same build.

### Fixture and isolation contracts

- Never touches the main checkout, the developer's `:3000` / `:3175`, a personal
  browser profile, existing containers/volumes, or a user's desktop vault.
- Browser reuses the retained Phase 0 generator (large: 4,500 paints / 1,500
  miniatures / 300 schemes / 500 templates; stress: 30,000 / 10,000 / 3,000 / 5,000),
  then adds 360 focused synthetic miniatures, two retained paints and a user scheme.
  Thus its totals differ from the unchanged in-process benchmark fixtures. It uses
  a random loopback port and `phase3-miniatures.localhost` in a fresh Chromium context.
- After fixture creation, browser **restarts both server and Chromium** before the
  measured default-Home document. Fresh process is **not cold disk**. Native and
  Docker startup observations occur after setup/seeding, not cold server measurements.
- Native first-run chooses local/remote normally, with separate temporary desktop
  profiles and a separate remote fixture server. Updates are disabled. Both modes
  intentionally quit and relaunch, verify the retained connection/owner, perform
  normal owner sign-in again (desktop proxy cookies are intentionally in memory),
  verify the retained fixture, and intentionally quit again. The original desktop vault is never opened, so
  there is no user connection to restore.
- Docker uses a unique ownership-labelled volume, localhost random published port,
  and immutable image ID. Only its own labelled container is stopped/removed;
  fixture volume is retained, not pruned.
- Commands seed through the **production API**, including UUID IDs generated by
  normal commands. The broken recipe is legal cascade behavior: create a valid
  substitution, enable it as default, delete its sole custom ingredient. The target
  remains physically owned with quantity two but its active recipe is empty/broken.
  No raw SQL fixture mutation, import bypass, or test hook is required.
- The final fixture item is discovered by production cursor pagination rather
  than guessed from insertion order (created timestamps can share a millisecond).

### Shared checklist

1. Default **Workbench/Home**, bounded 48-row requests (96 rows with automatic viewport prefetch in the observed viewport), server counts, projection/startup JSON bytes,
   usable-paint observation time, SSE open, **zero `/api/state`**.
2. Home painting-stage and Miniatures ownership filters; server fuzzy search.
3. Multiple loaded pages: independent stock write changes readiness, every loaded page
   refreshes to one revision, exact scroll offset retained; restore stock.
4. More than five pages, final item reachable, viewport-bounded tile DOM.
5. Tab and Shift+Tab across virtualization boundary; Return opens, Escape dismisses.
6. Edit notes and change painting status; reopen and verify both persisted.
7. Attach scheme, reopen, detach scheme, reopen and verify persistence.
8. Physically-owned original with empty active recipe remains red/broken.
9. Zero legacy snapshot requests and zero renderer/GraphQL exceptions throughout.

Both native modes use a **separate standalone Node process and fresh bearer login
session for each stock write**, outside Electron and proxy cookies. For local,
read-only `ps` metadata identifies exactly one direct bundled Node child of the
harness-owned Electron PID; `lsof` identifies that child's sole IPv4-loopback
listener. `/tmp` is canonicalized to `/private/tmp` on macOS. Unowned, ambiguous,
non-loopback or non-HTTP endpoints are rejected. No application diagnostics hook
or production runtime change is needed. Browser and Docker use a distinct Node
HTTP bearer client/session outside the renderer, but within the harness process.

All raw request bodies omit authentication credentials through the retained
recorder; auth response bodies are not retained. Record logs, screenshots, fixture
paths, identities, PASS/FAIL/PARTIAL/NOT RUN counts and failure stacks are preserved.
Tests (9 total): `node --test scripts/home-miniatures-fixture.test.mjs scripts/home-miniatures-process-client.test.mjs scripts/library-smoke-support.test.mjs scripts/smoke-library-native.test.mjs`.
The fixture test uses real production API routing in-process in a fresh temporary
database and proves the broken cascade, physical stock, readiness, complete
pagination and final item contract. It does **not** establish browser/native UI success.

No full-native-control sweep, Windows/Linux desktop, signing/notarization, offline
remote operation, release deployment, or large-vault latency guarantee is claimed.
Timings are single end-to-end observations including harness/navigation/render,
not percentiles. Completed API bytes exclude unbounded SSE and JS/CSS/fonts; list
payload savings are not an equivalent reduction in the application bundle.
