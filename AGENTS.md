# Repository Guidelines

## Project Structure & Module Organization

Paint Vault is an Nx workspace. The NestJS server and API handlers are in `apps/paint-vault/`, and the Vite app frontend is in `apps/paint-vault-web/`. The separate Astro product website is in `apps/paint-vault-site/`: Astro routes are in `src/pages/`, React and MUI page content is in `src/site/`, and its images are in `public/images/`. The shared app interface is in `packages/vault-ui/src/dom/`. The app web entry point and Electron connection chooser are in `apps/paint-vault-web/src/`; `apps/paint-vault-electron/` contains the macOS and Windows desktop host, preload bridge, and packaged server. Put reusable paint rules and search logic in `packages/paint-core/`, and server-only helpers in `apps/paint-vault/lib/`. Database schema and seed code are in `apps/paint-vault/db/`, with generated migrations in `apps/paint-vault/drizzle/`. Web SQLite data and uploaded images remain in the repository-root `data/` directory. Desktop vaults use separate platform application-data folders.

## Build, Test, and Development Commands

Use Node.js 22.13 or newer. Run `npm ci` at the repository root to install the locked dependencies, then `npm run dev` to serve the Vite app at `http://localhost:3000` with `/api` proxied to NestJS on port 3175. Run `npm run site:dev` to serve the separate Astro website at `http://127.0.0.1:4321`; `npm run site:build` builds only that site. Run `npm run storybook` to browse the shared UI components at `http://localhost:6006`; `npm run storybook:build` builds a static copy, and `npm run storybook:test` runs every story as a test in headless Chromium, failing on render errors, play-function failures, and accessibility violations (run `npx playwright install chromium` once first). Root scripts run Nx targets: `npm run lint` for ESLint and TypeScript diagnostics, `npm test` for the Node tests, and `npm run build` for the app and website production builds. Run `npm run format:check` to check source formatting and `npm run format:write` to apply it. `npm run start` serves the app frontend and API from one NestJS address; it does not serve the product website. Prefer the repository's Nx wrapper for direct targets, such as `node scripts/nx.mjs test @paint-vault/core`. After changing `apps/paint-vault/db/schema.ts`, run `npm run db:generate` and include the resulting `apps/paint-vault/drizzle/` files.

Run `npm run desktop` on macOS or Windows to build the web UI and bundled server, then launch Electron. Run `npm run desktop:package` on the target operating system to build a distributable app. After server changes, regenerate the packaged server with the normal launcher or `node scripts/package-desktop-server.mjs electron`; rebuilding only the Electron window does not regenerate that server. The packaging script refuses to run unless Node matches `.nvmrc` exactly, and it installs the server's production dependencies from the root `package-lock.json`, so the web server, Docker image, and desktop app run the same library versions; `.nvmrc` also sets the Node version for Docker and CI, so change them together. Run the built server from its `dist/` or packaged `server/` directory so it can find its Drizzle migrations.

## Coding Style & Naming Conventions

Follow the existing two-space indentation and TypeScript style. Use PascalCase for React components and types, camelCase for functions and variables, and descriptive lowercase file names such as `fuzzy-search.ts`. React component files are named after their component in PascalCase, such as `LibraryPaintRow.tsx`. Keep shared behavior in a component, app `lib/` module, or `packages/paint-core/` instead of duplicating it across screens. Shared screens use React DOM and MUI components; preserve responsive behavior at phone and desktop widths. Home, Miniatures, miniature drawer/detail, Library, paint detail, paint autocomplete and substitution dialogs read typed Apollo projections through `packages/vault-ui/src/dom/graphql/` hooks; use `usePaintStock()` for migrated inventory actions and `useMiniatureActions()` for miniature/recipe/scheme-attachment commands. Home is the default screen and must not initialize `/api/state`; only unmigrated screens and source/scheme data overlays opt into the snapshot lazily. Never manufacture a partial `State` from pages or read the legacy snapshot on the migrated path. Read queries use `no-cache` until the invalidation controller accepts their generation/revision, then commit the complete loaded window atomically. Keep server-derived availability/counts; only raw inventory is optimistic. Unmigrated screens still read `useVault()` from the TanStack snapshot/row-delta cache. Shared actions and app screen state use `useVaultStore(selector)`; do not pass the vault, `api`, `notify`, or paint-state setters down as props. Zustand holds actions and screen state only. See `docs/graphql-library.md` and `docs/graphql-miniatures.md` for projection, pagination, search and coexistence contracts. Stories get the sample vault and spy actions from the global Storybook decorator, and a story can supply other data with `parameters: { vault }`. Give each reusable component in `packages/vault-ui/src/dom/Components/` a `*.stories.tsx` file beside it, using the sample data and wrappers in `packages/vault-ui/src/dom/storybook/`. Run `npm run format:check`, `npm run lint`, `npm test`, and `npm run storybook:test` before submitting changes. See `docs/code-quality.md` for rule adaptations.

For the product website, keep Astro route files thin and implement interactive content in React components. Use MUI `sx` or React `style` props for styling; do not add `.css` files. Give meaningful images alt text, label illustrative interface previews, and keep generated assets in `apps/paint-vault-site/public/images/`. Check the homepage, docs, FAQ, and download page at desktop and phone widths after visual changes. Keep setup instructions and feature claims aligned with the app and README. Desktop download links point to the repository's Releases page; verify that the intended packages exist before describing them as available.

## UI Parity & Desktop Compatibility

Preserve the MUI appearance and interactions in the shared React UI. Compare reference and current screens at matching viewport sizes and equivalent data states. Match typography, spacing, labels, placeholders, field states, autocomplete behavior, keyboard handling, and responsive grid breakpoints. Keep the current Settings design. Implement missing behavior in shared components instead of duplicating it between web and Electron.

Use the shared `packages/vault-ui/src/dom/Components/Modal.tsx` component for new app forms and confirmation overlays. It provides the app's dialog on desktop and its responsive presentation on phones. Reuse `Modal` and its `ModalHeader` rather than creating a second modal or dialog wrapper or using a bare MUI `Dialog` for these flows.

In project recipe edit mode, place the dashed `+ Add Scheme` control after the scheme cards in their grid, including when no schemes are attached. Keep it consistent with the dashed `+ Add a step` control that follows the paint steps. Keep these add actions with the content they extend.

Keep text at WCAG AA contrast (4.5:1 for small text) and give buttons accessible names that include their visible text; the story tests check both.

Never programmatically focus a text field or autocomplete. Do not use `autoFocus` or call `.focus()` on text inputs, textareas, selects, or autocomplete controls. Let the user choose when to focus these fields. Keyboard focus handoff for non-text controls is allowed when needed for navigation.

Keep desktop-specific backup export and server selection behind the Electron preload bridge; keep the shared UI usable in a normal browser without that bridge. On first Electron launch, the user chooses the bundled local server or an existing server. Persist that choice separately from vault data, and allow switching in Settings. In remote mode, do not start the bundled server. Verify shared changes separately in the web app and packaged desktop app. For large collections, preserve viewport-based rendering, stable columns during resize, and access to the final item after scrolling or filtering.

Build the desktop server on its target operating system so `better-sqlite3` uses the correct native binary. Rebuild and relaunch the Electron package after main-process, preload, or server changes.

## Testing Guidelines

Tests use Node's built-in test runner and `node:assert/strict`. Name test files `*.test.ts` beside the logic they cover, or `*.test.mjs` / `*.test.cjs` for JavaScript modules. Add focused tests for business rules, search behavior, database changes, and Electron connection parsing; check interactive UI changes in the running app. Run `npm test` and `npm run lint` before a pull request.

### Desktop Smoke Tests

- Test the actual packaged Electron app used by the normal launcher. Set `PAINT_VAULT_DISABLE_UPDATES=1` so the test build never downloads or installs a published release. Record its path/build identity and the test time so crash reports can be matched to the correct binary. Confirm the renderer loads and, in local mode, the bundled server starts before testing controls.
- Keep a checklist with `PASS`, `FAIL`, `PARTIAL`, `NOT RUN`, and `N/A`, plus evidence and a reason for exclusions. Report completed and remaining counts accurately. A successful build, source review, or web test does not establish a native UI pass.
- For a full smoke test, exercise first-run server selection and owner setup, then every available button and editable field across navigation, collection/model/paint/scheme screens, add/edit/delete flows, recipes and substitutions, images, sharing/export, imports/backups, server switching, and account settings. Verify save results by reopening records. Exercise cancellation, validation, and relevant retry paths.
- Check mouse and keyboard interaction, including Tab/Shift+Tab, Return submission, Escape dismissal, dropdown selection, and repeated reordering in both directions. Check image zoom/pan/reset, file selection, backup export, and shopping-list sharing. Test narrow and desktop widths, long content, scrolling, and visibility of the drawer's bottom section.
- Inspect Electron crash reports and logs after unexpected exits. Distinguish an intentional quit from a crash. After a repair, rebuild when necessary, retest the failing interaction in the packaged app, and finish the remaining checklist. An empty log alone is not a smoke-test pass.
- Remove temporary diagnostics and test-only Electron hooks before the final build and smoke pass.
- When a check requires user action, identify the exact control and why intervention is needed, then continue independent checks. Keep credentials out of chat, logs, and screenshots. Record user-confirmed results separately from directly observed results; leave unverified checks pending.
- At closeout, restore the original server connection, verify the original vault, and test an intentional quit/relaunch. Stop only test processes started for the task. Retain fixture data and recovery backups unless cleanup is authorized.

## Commits & Pull Requests

Recent commits use short, imperative subjects such as `Add fuzzy search across the app`; some use a `feat:` prefix. Keep subjects specific and use either pattern consistently within a change. Pull requests should explain the user-visible behavior, list verification commands, link relevant issues when available, and include screenshots for visual changes. Call out schema migrations or data compatibility concerns explicitly.

## Catalog Sources

Paints, schemes, and templates are installed from user-added GitHub sources; none of the original catalog is bundled or seeded. `docs/source-format.md` specifies the source format, and `apps/paint-vault/lib/source-format.ts` enforces it; change them together, and treat a field change as a new format version. `docs/plugins.md` documents install, update, removal, and backup behavior; update it when that behavior changes. `examples/demo-plugin/` is the sample plugin, and `apps/paint-vault/lib/demo-plugin.test.ts` installs it, so update both with any format change. The preserved original catalog lives outside this repository in the sibling `prepared-catalog/` folder for publication as its own source. Do not add its catalog JSON or images to this repository. Paints have a color hex value and no image URL; scheme and template images remain supported.

## Configuration & Data Safety

The defaults need no `.env` file; `PAINT_VAULT_PORT` changes the Docker host port. Owner setup is required, and the owner can require sign-in for vault data. A server not bound only to loopback prints a one-time setup code to its log, and setup needs that code. Password attempts are limited per client address; Forwarded headers (`X-Forwarded-For`, `-Host`, `-Proto`) are trusted only when `PAINT_VAULT_TRUST_PROXY=1` is set for a server behind a reverse proxy. Against DNS rebinding, a server with sign-in off (and the desktop server always) answers only to IP addresses, `localhost` names, and names in `PAINT_VAULT_ALLOWED_HOSTS`; keep that check when changing routing. The server sends a CSP and framing, sniffing, and referrer headers on every response; a page or route that needs a looser policy must set its own. When sign-in is disabled, expose the server only on a trusted network or behind an authenticated reverse proxy. Do not commit `data/`, secrets, or uploaded photos.

Run web smoke-test mutations against an isolated `DATA_DIR` on a separate loopback port. For Electron, set `PAINT_VAULT_DESKTOP_DATA_DIR` to a new absolute directory before launch; it isolates both the connection choice and local vault. Preserve the user's original vault and take a recovery backup before destructive fixture tests. Verify deletion cascades and repeated backup restores without changing unrelated records. Stop only the fixture processes owned by the task, and retain fixture data and recovery backups unless cleanup is authorized.

Authentication cookies are scoped by hostname, not port. Test servers on the same hostname can replace the original server's `pv_session` cookie; use a distinct test hostname where practical and allow for re-authentication when restoring the original connection. Never interpret a lost session as lost vault data without checking.
